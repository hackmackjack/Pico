    for char in string:

wlan.active(True)

## 1. Project 2402: Asynchronous Professional REST API Client Handler

### 2. Learning Objective
Fetch data in pages (Pagination) without blocking the main loop. Process Page N while downloading Page N+1.

### 3. Concepts Introduced
*   **Pagination**: Splitting large datasets into chunks (Pages).
*   **Prefetching**: Starting the next task before the current one finishes.
*   **Asynchrony**: Non-blocking IO.

### 4. Hardware Required
*   **Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (WiFi Connection)

### 6. Blocks Used
*   **from Network & IoT, drag `connect_wifi`**
*   **from AsyncRequests, drag `async_get`**
*   **from Loops, drag `pico_forever`**

### 7. Variables
*   **page** (Number)
*   **next_task** (Future)
*   **data** (String)

### 8. Step-by-Step Guide

**A. Initialization**
1.  **Setup**: Connect WiFi. Set `page` to **1**.

**B. Pipeline**
2.  **Start First Fetch**:
    *   From **AsyncRequests**, set `next_task` to `async_get` (".../data?page=1").
3.  **Loop**:
    *   From **Loops**, drag `while` True.
    *   **Await**: Set `data` to `await` `next_task`.
    *   **Trigger Next**:
        *   Change `page` by 1.
        *   Set `next_task` to `async_get` (".../data?page=" + `page`).
    *   **Process Current**:
        *   From **Text**, print "Processing Page " + (`page` - 1).
        *   from **Smart IO**, wait 1s (Simulate math).

### 9. Execution Flow
1.  **Request 1**: Browser sends req for Page 1.
2.  **Process 1 & Request 2**: While CPU parses Page 1, Network chip fetches Page 2.
3.  **Efficiency**: Total time = Max(Compute, Network) instead of Sum(Compute, Network).

### 10. Generated Code
``python
import uasyncio

async def fetch_page(p):
    print(f"Fetching {p}...")
    # Simulates network request
    await uasyncio.sleep(0.5) 
    return f"Data {p}"

async def main():
    page = 1
    # Start first
    future = uasyncio.create_task(fetch_page(page))
    
    while page < 5:
        # Wait for result
        data = await future
        print(f"Processing {data}")
        
        # Start next immediately
        page += 1
        future = uasyncio.create_task(fetch_page(page))
        
        # Simulate processing time
        await uasyncio.sleep(0.5)

uasyncio.run(main())
``

### 11. Common Mistakes
*   **Await in Loop**: `data = await fetch(); process(data)` is synchronous. Must trigger `fetch_next` *before* `process(current)` to be parallel? Actually, in single-thread asyncio, you await the Future processing. True parallelism requires threads, but async overlaps IO wait.

### 12. Try This Next
*   **Stop Condition**: Stop if API returns "Next: null".
*   **Retry**: If fetch fails, retry before processing.

    *   **Method `get(path)`**:
        *   Construct full URL: `self.base_url` + `path`.
        *   Headers: `{"Authorization": self.api_key}`.

**B. Usage**

        self.base = base
        self.headers = {"Authorization": "Bearer " + key}
        
    def get(self, endpoint):

        return urequests.get(url, headers=self.headers)

client = RestClient("http://api.site.com", "xyz123")
res = client.get("/users")
``

### 11. Common Mistakes

## 1. Project 2404: Robust Professional REST API Client Controller

### 2. Learning Objective
Protect the server from "Thundering Herd" attacks. Add random delays to initialization sequences.

### 3. Concepts Introduced
*   **Thundering Herd**: Many clients connecting simultaneously (e.g., after power outage).
*   **Jitter**: Adding random variation to timing.
*   **Backoff**: Increasing delay after failures.

### 4. Hardware Required
*   **Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (WiFi Connection)

### 6. Blocks Used
*   **from Math, drag `random_int`**
*   **from Smart IO, drag `pico_wait`**
*   **from Network & IoT, drag `connect_wifi`**

### 7. Variables
*   **delay** (Number)

### 8. Step-by-Step Guide

**A. Startup Logic**
1.  **Calculate Jitter**:
    *   From **Math**, set `delay` to `random_int`(0, 5000) (ms).
    *   From **Text**, print "Waiting " + `delay`.
2.  **Wait**:
    *   from **Smart IO**, wait `delay` ms.
3.  **Connect**:
    *   From **Network & IoT**, connect WiFi.
4.  **Request**:
    *   Fetch Data.

### 9. Execution Flow
1.  **Power On**: 100 Picos turn on.
2.  **Jitter**:
    *   Pico A waits 0.1s.
    *   Pico B waits 4.9s.
3.  **Spread**: Requests hit server over 5 seconds instead of 0.01s.
4.  **Result**: Server survives.

### 10. Generated Code
``python
import utime
import urandom

# Random startup delay 0-5s
jitter = urandom.randint(0, 5000)
print(f"Jitter wait: {jitter}ms")
utime.sleep_ms(jitter)

# Now connect
wlan.connect()
``

### 11. Common Mistakes
*   **Fixed Delay**: Waiting 2s on ALL devices just shifts the spike by 2s. Must be *Random*.
*   **Seeding**: If `urandom` isn't seeded, all Picos might pick the same "Random" number. (Use ADC noise to seed).

### 12. Try This Next
*   **Exponential Backoff**: If WiFi fails, wait 1s, then 2s, then 4s, then 8s.
*   **Slotting**: Assign fixed time slots based on Device ID (ID 1 @ :01, ID 2 @ :02).

## 1. Project 2405: Professional REST API Client with Error Handling

### 2. Learning Objective
Implement the "Circuit Breaker" pattern. Stop calling a failing API to prevent system hang/cascading failure.

### 3. Concepts Introduced
*   **Circuit Breaker**: Closed (Normal), Open (Broken/Wait), Half-Open (Test).
*   **Failure Threshold**: Number of errors before "Tripping".
*   **Reset Timeout**: Time to wait before trying again.

### 4. Hardware Required
*   **Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (WiFi Connection)

### 6. Blocks Used
*   **from Logic, drag `controls_if`**
*   **from Variables, drag `variables_set`**
*   **from Requests, drag `get_request`** (with Try/Catch)

### 7. Variables
*   **failures** (Number)
*   **state** (String: "CLOSED", "OPEN")
*   **last_fail** (Time)

### 8. Step-by-Step Guide

**A. Initialization**
1.  **Setup**: Set `state` = "CLOSED". `failures` = 0.

**B. Loop**
2.  **Check State**:
    *   Start Loop.
    *   **If OPEN**:
        *   If (Time - `last_fail`) > 60s: Set `state` = "HALF-OPEN".
        *   Else: Print "Skipping (Open)". Continue.
3.  **Attempt**:
    *   **Try**:
        *   `get_request`("api.com").
        *   Set `failures` = 0. Set `state` = "CLOSED".
    *   **Catch (Error)**:
        *   Increment `failures`.
        *   If `failures` >= 5: Set `state` = "OPEN". Record `last_fail` Time.

### 9. Execution Flow
1.  **Normal**: API works, failures = 0.
2.  **Outage**: API fails 5 times.
3.  **Trip**: State becomes OPEN.
4.  **Cool Down**: Pico stops sending requests for 60s.
5.  **Recovery**: After 60s, tries one request. If Success -> CLOSED.

### 10. Generated Code
``python
failures = 0
state = "CLOSED"
COOLDOWN = 60

while True:
    if state == "OPEN":
        if (utime.time() - last_fail) > COOLDOWN:
            state = "HALF-OPEN"
        else:
            print("Circuit Open. Waiting...")
            utime.sleep(1)
            continue
            
    try:
        req = urequests.get(url)
        # Success
        failures = 0
        state = "CLOSED"
    except:
        failures += 1
        if failures >= 5:
            state = "OPEN"
            last_fail = utime.time()
            print("Tripped!")
``

### 11. Common Mistakes
*   **Infinite Retry**: Looping tight on error (DDoS yourself).
*   **No Reset**: Circuit never closes even after API comes back.

### 12. Try This Next
*   **Fallback**: If Circuit Open, read data from Cache/SD Card instead.

## 1. Project 2406: Optimized Professional REST API Client Algorithm

### 2. Learning Objective
Negotiate data formats with the server to optimize bandwidth. Request highly compressed formats (MsgPack) instead of text (JSON).

### 3. Concepts Introduced
*   **Content Negotiation**: The `Accept` header (`application/json` vs `application/x-msgpack`).
*   **Binary Protocols**: MsgPack/Protobuf are smaller and faster to parse than JSON.
*   **Overhead**: JSON has braces `{}` and keys. Binary removes them.

### 4. Hardware Required
*   **Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (WiFi Connection)

### 6. Blocks Used
*   **from Requests, drag `request_with_headers`**
*   **from Variables, drag `variables_set`**
*   **from Logic, drag `controls_if`** (Compare Sizes)

### 7. Variables
*   **headers** (Dictionary)
*   **json_size** (Number)
*   **bin_size** (Number)

### 8. Step-by-Step Guide

**A. JSON Request**
1.  **Header**: Set `Accept` to "application/json".
2.  **Fetch**: Get Data. Record `json_size` (Length of response).

**B. Binary Request**
1.  **Header**: Set `Accept` to "application/msgpack".
2.  **Fetch**: Get Data. Record `bin_size`.

**C. Compare**
1.  **Print**: "Saved " + (`json_size` - `bin_size`) + " bytes".

### 9. Execution Flow
1.  **Scenario**: Sending 1000 temperature readings.
2.  **JSON**: `[{"t": 25.0}, {"t": 25.1}...]` (~12 bytes per reading).
3.  **MsgPack**: `\x92\x19...` (~4 bytes per reading).
4.  **Result**: 3x bandwidth savings.

### 10. Generated Code
``python
import urequests

url = "http://api.example.com/data"

# JSON
h1 = {"Accept": "application/json"}
r1 = urequests.get(url, headers=h1)
s1 = len(r1.content)
print(f"JSON Size: {s1}")

# MsgPack
h2 = {"Accept": "application/x-msgpack"}
r2 = urequests.get(url, headers=h2)
s2 = len(r2.content)
print(f"MsgPack Size: {s2}")

print(f"Savings: {s1 - s2} bytes")
``

### 11. Common Mistakes
*   **Server Support**: If the server doesn't support MsgPack, it will ignore the header and send JSON anyway (or 406 Not Acceptable).
*   **Debuggability**: You can't print binary data easily to console. Harder to debug than JSON.

### 12. Try This Next
*   **Compression**: Use `Accept-Encoding: gzip` (If Pico supports decompression).
*   **CSV**: Use `text/csv` for tabular data.

## 1. Project 2407: Professional REST API Client Data Pipeline

### 2. Learning Objective
Implement a bidirectional synchronization loop. Pull cloud state, diff with local state, apply changes, and push confirmation.

### 3. Concepts Introduced
*   **Twin State**: Desired State (Cloud) vs Reported State (Device).
*   **Diffing**: Determining what changed.
*   **Convergence**: The process of making Reported == Desired.

### 4. Hardware Required
*   **Raspberry Pi Pico W**
*   **1 LED** (Simulated Output)

### 5. Wiring / Interfaces
*   **LED** -> GP15

### 6. Blocks Used
*   **from Network & IoT, drag `connect_wifi`**
*   **from Objects, drag `json_parse`**
*   **from Logic, drag `controls_if`**
*   **from Requests, drag `post_request`**

### 7. Variables
*   **cloud_state** (Object)
*   **local_state** (Object)
*   **led_status** (Boolean)

### 8. Step-by-Step Guide

**A. Pull (Desired)**
1.  **Get**: Fetch `http://cloud.com/device/config`.
2.  **Parse**: Convert JSON to `cloud_state`.

**B. Diff & Apply**
1.  **Check**: If `cloud_state["led"]` != `local_state["led"]`:
    *   Set **GP15** to `cloud_state["led"]`.
    *   Set `local_state["led"]` to `cloud_state["led"]`.
    *   Set `dirty` = True.

**C. Push (Reported)**
1.  **Check**: If `dirty` is True:
    *   **Post**: Send `local_state` to `http://cloud.com/device/reported`.
    *   Print "Synced".

### 9. Execution Flow
1.  **User**: Toggles switch in Web App. Cloud Desired = ON.
2.  **Pico**: Polls cloud. Sees Desired=ON. Local=OFF.
3.  **Action**: Turns LED ON. Updates Local=ON.
4.  **Ack**: Tells Cloud "I am now ON".
5.  **UI**: Web App shows Green Checkmark.

### 10. Generated Code
``python
local = {"led": False}

while True:
    # Pull
    res = urequests.get("http://cloud.com/desired")
    desired = res.json()
    
    # Diff
    if desired["led"] != local["led"]:
        print("Updating LED...")
        led.value(desired["led"])
        local["led"] = desired["led"]
        
        # Push
        urequests.post("http://cloud.com/reported", json=local)
``

### 11. Common Mistakes
*   **Race Conditions**: If User toggles fast (ON-OFF-ON), polling might miss the middle state.
*   **Bandwidth**: Polling every 1s is expensive. Use Long Polling or MQTT if possible.

### 12. Try This Next
*   **Version Number**: Ignore config if `version` < `current_version`.
*   **Reboot**: If config says `reboot: true`, restart Pico.

## 1. Project 2408: Secure Professional REST API Client Interface

### 2. Learning Objective
Verify the identity of the server to prevent Man-In-The-Middle (MITM) attacks. Compare the SSL Certificate fingerprint.

### 3. Concepts Introduced
*   **MITM Attack**: A hacker intercepts WiFi and pretends to be "api.google.com".
*   **Certificate**: Digital ID Card.
*   **Pinning**: Hardcoding the expected ID Card hash.

### 4. Hardware Required
*   **Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (WiFi Connection)

### 6. Blocks Used
*   **from Network & IoT, drag `connect_wifi`**
*   **from Crypto, drag `sha256`** (Conceptual)
*   **from Requests, drag `get_request`**

### 7. Variables
*   **expected_hash** (String)
*   **server_cert** (Bytes)

### 8. Step-by-Step Guide

**A. Setup**
1.  **Hardcode**: Set `expected_hash` to "A1 B2 C3..." (SHA256 of server public key).

**B. Connection**
1.  **Socket**: Open SSL Socket to server.
2.  **Get Cert**: Retrieve binary certificate.
3.  **Hash**: Calculate SHA256 of cert.

**C. Validation**
1.  **Compare**:
    *   If `calced_hash` == `expected_hash`: Proceed.
    *   Else: **Abort Connection**. Print "SECURITY ALERT: UNTRUSTED SERVER".

### 9. Execution Flow
1.  **Connect**: Pico calls Server.
2.  **Handshake**: Server sends Cert.
3.  **Check**: Pico checks if this is the *real* server it knows.
4.  **Result**: If Hacker proxies the connection, their Cert won't match. Connection drops.

### 10. Generated Code
``python
import ussl
import usocket

# MicroPython 'ussl' is limited. 
# Full pinning usually requires checking the der format manually.
# This code simulates the check.

def verify_pin():
    sock = usocket.socket()
    addr = usocket.getaddrinfo("google.com", 443)[0][-1]
    sock.connect(addr)
    
    # Wrap
    sslsock = ussl.wrap_socket(sock)
    
    # Get DER (Simulated - MPy doesn't always expose getpeercert() cleanly)
    cert = sslsock.getpeercert(True) 
    
    # Hash it
    import uhashlib
    h = uhashlib.sha256(cert).digest()
    
    if h == EXPECTED_BYTES:
        print("Secure")
    else:
        print("MITM Detected!")
        sslsock.close()
``

### 11. Common Mistakes
*   **Cert Rotation**: If Google updates their certificate (every 3 months), your hardcoded Hash fails and devices brick. Use **Public Key Pinning** or Pin Root CA to avoid this.

### 12. Try This Next
*   **Backup Pin**: Hardcode 2 hashes (Primary and Backup).
*   **Time Check**: Verify `NotBefore` and `NotAfter` dates (Requires accurate RTC).

## 1. Project 2410: Industrial Professional REST API Client Solution

### 2. Learning Objective
Reverse the roles. Act as a Server to receive "Webhooks" (Event Notifications) from the Cloud.

### 3. Concepts Introduced
*   **Webhook**: HTTP POST sent *to* you when something happens.
*   **Listening Server**: Binding a socket to Port 80.
*   **Payload Parsing**: Extracting data from the incoming Request Body.

### 4. Hardware Required
*   **Raspberry Pi Pico W**
*   **Relay** (Simulated Industry Action)

### 5. Wiring / Interfaces
*   **Relay** -> GP15

### 6. Blocks Used
*   **from Network & IoT, drag `start_server`**
*   **from Loops, drag `server_poll`**
*   **from Text, drag `get_json_body`**

### 7. Variables
*   **request** (Object)
*   **action** (String)

### 8. Step-by-Step Guide

**A. Setup Server**
1.  **Bind**: Start Server on Port 80.
2.  **Print**: "Listening on IP: ..."

**B. Handle Request**
1.  **Loop**:
    *   Wait for Client.
    *   **Receive**: Get `request`.
    *   **Parse**: Extract JSON Body.
    *   **Logic**:
        *   If `body["action"]` == "OPEN_VALVE":
            *   Set **Relay** HIGH.
        *   Else:
            *   Set **Relay** LOW.
    *   **Respond**: Send "HTTP/1.0 200 OK".

### 9. Execution Flow
1.  **Event**: Factory machine finishes job. Cloud detects this.
2.  **Webhook**: Cloud sends `POST http://<PICO_IP>/hook` with `{"action": "OPEN_VALVE"}`.
3.  **Receive**: Pico wakes up, parses JSON.
4.  **Act**: Relay clicks ON.
5.  **Reply**: Pico says "OK". Cloud marks event as delivered.

### 10. Generated Code
``python
import socket

addr = socket.getaddrinfo('0.0.0.0', 80)[0][-1]
s = socket.socket()
s.bind(addr)
s.listen(1)

print('listening on', addr)

while True:
    try:
        cl, addr = s.accept()
        request = cl.recv(1024)
        # Rudimentary parsing - assumes Body is at end

*   **current_val** (Number)
*   **last_sent_val** (Number)
*   **delta** (Number)

### 8. Step-by-Step Guide

**A. Measure**
1.  **Read**: Set `current_val` to Sensor Value.

**B. Compare**
1.  **Calculate**: Set `delta` = `abs`(`current_val` - `last_sent_val`).
2.  **Check**:
    *   If `delta` > 0.5:
        *   **Send**: Upload `current_val`.
        *   **Update**: Set `last_sent_val` = `current_val`.

    *   Else:
        *   Print "Skipping (Change too small)".

2.  **T=1, Temp=25.2**: Change 0.2 < 0.5. No Upload.

### 2. Learning Objective
Implement a "Reliable Transfer" layer on top of UART. Send Acknowledge (ACK) packets to confirm data receipt.

### 3. Concepts Introduced
*   **QoS (Application Layer)**: BLE ensures packet integrity (CRC), but not delivery (if buffer full).
*   **ACK/NAK**: "I got it" / "I missed it".
*   **Timeout/Retry**: Resending if no ACK received.

### 4. Hardware Required
*   **Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (Wireless)

### 6. Blocks Used
*   **from Loops, drag `while`** (Retry loop)
*   **from Bluetooth, drag `write`**

### 7. Variables
*   **msg_id** (Number)
*   **ack_received** (Boolean)

### 8. Step-by-Step Guide

**A. Sender (Pico)**
1.  **Packet**: `ID:5|Data:Hello`.
2.  **Send**: Write to Phone.
3.  **Wait**:
    *   Loop 10 times (1s).
    *   If `ack_received` (ID=5) is True: Break.
    *   Else: Print "Retry...".

**B. Receiver (Phone Logic)**
1.  **Get**: `ID:5|...`.
2.  **Reply**: `ACK:5`.

### 9. Execution Flow
1.  **Send**: Packet 5 goes out.
2.  **Loss**: Interference blocks it.
3.  **Timeout**: Pico waits 1s. No ACK.
4.  **Retry**: Pico sends Packet 5 again.
5.  **Success**: Phone gets it. Sends ACK.
6.  **Next**: Pico moves to Packet 6.

### 10. Generated Code
``python
msg_id = 0
ack_flag = False

def send_reliable(data):
    global msg_id, ack_flag
    msg = f"{msg_id}:{data}"
    
    for i in range(3): # 3 Retries
        uart.write(msg)
        ack_flag = False
        
        # Wait for ACK
        start = utime.ticks_ms()
        while utime.ticks_diff(utime.ticks_ms(), start) < 500:
            if ack_flag: return True
            utime.sleep(0.01)
            
    return False # Failed
``

### 11. Common Mistakes
*   **Blocking**: Waiting for ACK stops everything else. Use Async for non-blocking reliability.
*   **Deadlock**: Sender waits for ACK. Receiver waits for Data. Neither talks.

## 1. Project 2446: Optimized Professional BLE UART Algorithm

### 2. Learning Objective
Maximize throughput by negotiating a larger MTU (Maximum Transmission Unit) and using "Write Without Response" to send data faster than 1KB/s.

### 3. Concepts Introduced
*   **MTU Negotiation**: Asking the phone "Can we speak in sentences (247 bytes) instead of words (20 bytes)?".
*   **Connection Interval**: The heartbeat of BLE (7.5ms to 4000ms). Faster heartbeat = More data.
*   **Overhead**: Headers take space. Larger packets = Less % overhead.

### 4. Hardware Required
*   **Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (Wireless)

### 6. Blocks Used
*   **from Bluetooth, drag `ble_mtu_exchange`**
*   **from Loops, drag `repeat`**

### 7. Variables
*   **long_string** (String)

### 8. Step-by-Step Guide

**A. Negotiate**
1.  **Event**: On Connect.
2.  **Request**: `exchange_mtu(247)`.
3.  **Result**: Phone agrees (e.g., 247 or 185 bytes).

**B. Blast Data**
1.  **Setup**: Create a 200-character string.
2.  **Loop**:
    *   Write `long_string`.
    *   No Delay.

### 9. Execution Flow
1.  **Default**: 20 bytes * (1000ms / 50ms) = 400 bytes/sec. Slow.
2.  **Optimized**: 240 bytes * (1000ms / 7.5ms) = 32,000 bytes/sec. Fast.
3.  **Result**: Firmware update takes 10s instead of 10 minutes.

### 10. Generated Code
``python
def on_connect(conn_handle):
    # Request Max MTU (247 is typical max for BLE 4.2)
    ble.gattc_exchange_mtu(conn_handle, 247)

def send_file(data):
    # Send in chunks of 240 (leaving room for headers)
    chunk_size = 240
    for i in range(0, len(data), chunk_size):
        chunk = data[i : i+chunk_size]
        uart.write(chunk)
``

### 11. Common Mistakes
*   **Phone Limitation**: iPhones often cap MTU at 185 bytes. Android varies. Always check the *result* of the negotiation.
*   **Packet Loss**: Sending too fast fills the internal TX buffer. You must check if buffer is full before writing.

*   **Throughput Test**: Send 1MB of data and measure start/stop time. Calculate KB/s.
*   **Compression**: Zip the data before sending (zlib) to effectively double the speed.

## 1. Project 2449: Multi-Threaded Professional BLE UART

### 2. Learning Objective
Process complex text parsing on a second core/thread so the robot's balancing loop (Main Thread) never jitters.

### 3. Concepts Introduced
*   **Producer-Consumer**: The UART IRQ (Producer) puts raw text into a Queue. The Parser Thread (Consumer) reads and processes.
*   **FIFO Queue**: First In, First Out buffer.
*   **Determinism**: Ensuring the motor update Loop runs exactly every 10ms.

### 4. Hardware Required
*   **Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (Wireless)

### 6. Blocks Used
*   **from Threading, drag `start_thread`**
*   **from Lists, drag `list_insert`** (Queue)

### 7. Variables
*   **queue** (List)
*   **cmd** (String)

### 8. Step-by-Step Guide

**A. UART IRQ (Instant)**
1.  **Rx**: Get char.
2.  **Action**: Push to `queue`. Return immediately.

**B. Parser Thread (Background)**
1.  **Loop**:
    *   If `queue` has data:
        *   Pop `cmd`.
        *   Parse (Split/Search/Analyze). This is slow.
        *   Update Global Config.

**C. Main Loop (Critical)**
1.  **Loop**:
    *   Balance Robot (PID Controller).
    *   Sleep exactly 10ms.

### 9. Execution Flow
1.  **Event**: Phone sends a 1KB config file (JSON).
2.  **IRQ**: Fires 100 times. Fills queue. Takes 0.001s total.
3.  **Thread 2**: Spends 0.5s parsing the JSON.
4.  **Thread 1**: Continues balancing the robot perfectly. No stumble.
5.  **Single Thread**: Robot would fall over while parsing the JSON.

### 10. Generated Code
``python
import _thread

queue = []
lock = _thread.allocate_lock()

def parser_thread():
    while True:
        item = None
        with lock:
            if len(queue) > 0:
                item = queue.pop(0)
        
        if item:
            process_complex_command(item) # Slow
        
        utime.sleep(0.01)

# Start consumer
_thread.start_new_thread(parser_thread, ())

# Producer (IRQ)
def on_rx(data):
    with lock:
        queue.append(data)
``

### 11. Common Mistakes
*   **Race Conditions**: Accessing the `queue` from both threads without a `Lock` causes memory corruption.
*   **Queue Size**: If Parser is too slow, Queue will explode. Limit size to 50 items.

### 12. Try This Next
*   **Priority**: High priority commands ("STOP") bypass the queue and set a flag immediately.
*   **Feedback**: Parser thread writes "Processing..." back to UART.

## 1. Project 2454: Robust Professional Pico-to-Pico Radio Controller

### 2. Learning Objective
Implement "Reliable Delivery". If a packet is lost, retry until ACK received.

### 3. Concepts Introduced
*   **ACK (Acknowledgement)**: "I got it".
*   **Retry Limit**: Try 3 times, then give up (Timeout).
*   **Sequence ID**: Distinguishing "New Message" from "Retry of Old Message".

### 4. Hardware Required
*   **2x Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (Wireless)

### 6. Blocks Used
*   **from Loops, drag `repeat_until`**
*   **from Logic, drag `if_else`**

### 7. Variables
*   **seq** (Number)

### 8. Step-by-Step Guide

**A. Sender**
1.  Send `MSG:1:Hello`. Start Timer.
2.  Wait for `ACK:1`.
3.  If Timeout: Send again.

**B. Receiver**
1.  Recv `MSG:1`.
2.  Send `ACK:1`.
3.  Pass to App. (If `MSG:1` comes again, just ACK, don't pass to App).

### 9. Execution Flow
1.  **Drop**: Msg 1 sent. Radio noise kills it.
2.  **Retry**: Sender timeouts (200ms). Resends Msg 1.
3.  **Success**: Receiver gets it. Sends ACK.
4.  **Done**: Sender gets ACK. Moves to Msg 2.

### 10. Generated Code
``python
def send_reliable(msg):
    global seq
    payload = f"{seq}:{msg}"
    
    for i in range(3): # 3 Retries
        e.send(peer, payload)
        
        # Wait ACK
        start = utime.ticks_ms()
        while utime.ticks_diff(utime.ticks_ms(), start) < 200:
            if e.any():
                _, resp = e.recv()
                if resp == f"ACK:{seq}".encode():
                    seq += 1
                    return True # Success
            utime.sleep(0.01)
            
    return False # Fail
``

### 11. Common Mistakes
*   **Blocking**: The retry loop blocks the CPU. Async retry is better but harder.
*   **Duplicate**: Without Seq ID, a retry might look like a *new* command (e.g., "Toggle LED" -> Toggles twice -> No change).

### 12. Try This Next
*   **Piggyback**: Send ACK inside the next Return Message to save packets.
*   **Windowing**: Allow 5 un-acked messages before stopping (TCP style).

## 1. Project 2455: Professional Pico-to-Pico Radio with Error Handling

### 2. Learning Objective
Detect corrupt data using CRC (Cyclic Redundancy Check) and handle signal loss.

### 3. Concepts Introduced
*   **CRC32**: A math fingerprint. rare for corrupted data to have the same fingerprint.
*   **Frequency Hopping**: Changing channels (1 -> 6 -> 11) to avoid a crowded frequency.

### 4. Hardware Required
*   **2x Raspberry Pi Pico W**

### 5. Wiring / Interfaces
*   (Wireless)

### 6. Blocks Used
*   **from Math, drag `crc32`** (Simulated)
*   **from Radio, drag `set_channel`**

### 7. Variables
*   **my_crc** (Number)

### 8. Step-by-Step Guide

**A. Send**
1.  `crc` = Calculate(Data).
2.  Send `Data + CRC`.

**B. Recv**
1.  Split Data, CRC.
2.  Calc `checks` = Calculate(Data).
3.  If `checks` != `CRC`: Throw away.

**C. Interference**
1.  If packet loss > 50%: Switch Channel.

### 9. Execution Flow
1.  **Noise**: Microwave oven turns on (2.4GHz). Band is dead.
2.  **Detection**: Receiver sees garbage or silence.
3.  **Hopping**: Both units switch to Ch 11. Comms resume.

### 10. Generated Code
``python
def send_checked(msg):
    # Simulated CRC (Sum)
    checksum = sum(msg.encode())
    packet = f"{checksum}|{msg}"
    e.send(peer, packet)

def on_recv(msg):
    parts = msg.split("|")
    chk_remote = int(parts[0])
    data = parts[1]
    
    if sum(data.encode()) == chk_remote:
        print("Valid")
    else:
        print("Corrupt")
``

### 11. Common Mistakes
*   **Hardware CRC**: ESP-NOW actually does CRC in hardware/firmware. Corrupt packets are usually discarded *before* Python sees them. This project is useful for streams *inside* the payload or generic 433MHz radios (HC-12) which don't check.
*   **False Positive**: It is mathematically possible (1 in 4 billion) for bad data to have the correct CRC.

### 12. Try This Next
*   **Channel Hop**: If CRC fails 10 times, switch both Picos to Channel 6 (Pre-agreed sequence).

*   **Overflow**: DMA is too fast, overwrites old data before you read it.
